- (idea by coach) Starburst resolution: a note is a fixed 96-byte TIP (note id, value, holder pubkey, tip signature) plus an optional history blob. The tip alone fits every channel including a BLE extended advert; history gossips separately

- (technique by coach) started Decision Tree Mapping - charting the wire-format forks and their downstream costs
- (idea by coach) Fork - account model vs bearer note: bearer note chosen. Branch cost: no cheap global balance query, the wallet must fold notes to display a total
- (idea by coach) Fork - prevent vs detect double-spend: detect. Branch cost: requires gossip and accepts a defined window of exposure, which must be stated in the threat-model screen
- (idea by coach) Fork - on conflict, destroy value vs reassign it: destroy. Branch risk: a griefing vector where you poison your own note to burn value someone else holds. Mitigation: poison the BRANCH, not the note lineage
- (idea by coach) Fork - divisible notes vs fixed denominations: fixed denominations (1/5/20/100) with splits producing child notes. Branch cost: exact payment needs change-making, which is a real algorithm and a genuinely fun UI problem
- (idea by coach) Fork - who makes change, sender splits vs receiver refunds: sender splits, because a receiver refund needs a second round-trip that half the channels physically cannot do
- (idea by coach) Fork - one-way vs two-way channels: design the ENTIRE protocol to work ONE-WAY, fire and forget. Two-way is an optimization. Forced by QR, chirp, SMS and satellite - and it is the highest-leverage architectural constraint in the whole project
- (idea by coach) Fork consequence - one-way means no ACK, so the sender must be able to prove they sent and the receiver must be able to claim without cooperation. The transferred note must therefore be a complete, self-contained, independently verifiable object
- (idea by coach) Fork - encrypt to recipient vs signed plaintext: encrypt to the recipient's key, so a relay carrying it through the mesh cannot read value or identity
- (idea by coach) Fork tension - but broadcast channels (ultrasonic to a room, BLE advert) have no single recipient. Resolution: TWO MODES - DIRECTED (encrypted to a key) and BEARER (anyone in earshot claims, first come). Bearer mode is the 'throw money in the air' demo
- (idea by coach) Fork - key discovery, pairing handshake vs continuous broadcast: recipients continuously advertise their public key over BLE, making 'being payable' a passive ambient state rather than an action
- (idea by coach) Fork - replay protection, per-transfer nonce vs enclave monotonic counter: counter, because nonces require remembering every nonce ever seen, which an offline device cannot bound
- (idea by coach) Fork - device clock vs logical clock: logical (Lamport-style counters on the endorsement chain), because offline device clocks are trivially wrong and attacker-controlled
- (idea by coach) Fork - encrypt the whole ledger DB vs only the keys: keys in the enclave, DB encrypted with an enclave-wrapped key. Full-DB encryption would destroy the 100k-row scroll benchmark, so the security choice and the benchmark choice are coupled
- (idea by coach) Fork - shared DB schema between the two apps: they MUST NOT share one (segregation), but the EXPORT format must be byte-identical so a wallet can migrate RN to Flutter - which is a second, quieter interop test

- (insight by coach) NFC REALITY CHECK - phone-to-phone NFC needs Host Card Emulation: a native Android service plus AID registration in the manifest, in BOTH frameworks. That is native work, not a plugin call, and Android Beam was removed in Android 10. NFC TAG read/write (write a note to a sticker, another phone reads it) is dramatically cheaper and still a genuine NFC demo. Recommendation: ship tag-based NFC, treat HCE as the stretch
- (insight by coach) BLE REALITY CHECK - raw BLE peripheral/advertising mode is the weak spot in both ecosystems; most libraries only do central. BUT the base repo already has expo-nearby-connections working, and Flutter has a mature nearby_connections package wrapping the SAME Google Nearby API. Using Nearby on both sides dodges the advertising problem entirely AND is a genuinely fair binding comparison because the underlying native API is identical
- (insight by coach) BLUETOOTH MESH REALITY CHECK - SIG Bluetooth Mesh is not realistic in a day. What is realistic and already anticipated in CLAUDE.md is APP-LAYER MULTI-HOP RELAY over the BLE/Nearby transport: TTL plus dedupe plus forward. That is pure TypeScript/Dart logic with no native code, so it is CHEAP once the transport works - and it is the same algorithm implemented twice, which makes it a clean language-level comparison
- (insight by coach) BIAS ESCALATION - the RN head start is now much larger than before. expo-nearby-connections is already integrated and building in the base repo, which is precisely the hardest channel. This must be measured from a clean scaffold and disclosed loudly, or the BLE/mesh numbers are worthless
- (decision by coach) REALIGNED CHANNEL PLAN - four drivers behind one interface, built in risk order: QR first (cheapest, camera already present), then Nearby Connections for BLE, then multi-hop relay as pure app logic on top, then NFC tag-based last (HCE as stretch).
